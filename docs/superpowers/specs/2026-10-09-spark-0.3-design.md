# Spark 0.3: in-terminal features

Spark stays a launcher plus a Claude Code mod. 0.3 adds six features from the steel-man/red-team review, all built on the mod API (`process.run`, `fs`, `tool.call`, `turn.start`/`turn.complete`, `ui.open` panes, the `AbovePrompt` band, `agent.list`). Out of scope: the custom code index and voice (rated skip), and macOS/Linux (Spark stays Windows-only).

## Features

1. **Failure capture.** `spark run -- <cmd>` runs a command in your own terminal, streams its output as usual, and on a non-zero exit writes `{ cmd, cwd, exitCode, output, at }` to `.git/spark-failure.json` (found with `git rev-parse --git-path`, so nothing shows in `git status`). The mod polls that file every 2 s. A new failure turns the band red (`✗ npm test failed (exit 1)`) with an `[ f: fix ]` button; `/spark-fix` does the same. Attaching fills the prompt box with the command, exit code and trimmed output (ANSI stripped, secrets redacted, passing-test lines dropped, last 80 lines). It is never sent on its own.
2. **Diff pane.** A `tool.call` hook notes every file Edit, Write, MultiEdit or NotebookEdit touches in the turn. The pane (`/spark-diff`, opened automatically on the first edit; the engine places it unasked only from 144 columns) shows `git diff` for those files with the engine's diff renderer; untracked files show as new with their line count, lockfiles as a one-line summary, at most 400 lines. The band always shows `n files +a −d`.
3. **Mascot states.** A one-row Sparky in the band changes face on state transitions only (no timer, so no flicker or redraw cost): idle, cooking, cooked, working, failure seen, sandbox review. `--plain`, `NO_COLOR` and SSH sessions get the plain `✦ spark` label.
4. **Sandbox (`/sandbox`).** Edits land in the real tree so the turn can build and run tests. Before each turn Spark snapshots the tree; when a turn ends with changes, the diff pane shows the whole turn against the snapshot with `[ k: keep ]` and `[ r: revert ]`. Revert restores the snapshot (after snapshotting the current state, so it can be undone). Deviation from the review: no separate worktree, because a mod can't move Claude Code's working directory and rewriting tool paths confuses the model.
5. **Snapshots.** Before every turn in a git repo Spark writes the whole working tree, untracked non-ignored files included, as a commit under `refs/spark/turn-N` using a separate index (`.git/spark-index`), so the real index, stash and branches are untouched. This covers what shell commands change, which Claude Code's `/rewind` doesn't. `/spark-restore` lists snapshots; `/spark-restore N` asks, snapshots the current state, then restores. The last 20 are kept. Database and network side effects can't be undone.
6. **Agents pane and merge gate (`/spark-agents`).** Lists subagents with status (refreshed every 2 s while any runs) and the repo's other worktrees. Each worktree has `[ test ]`, which links the main `node_modules` into it if missing and runs the detected test command there, and `[ merge ]`, enabled only after its tests pass, which runs `git merge --no-ff` of its branch. The MISP tells Claude not to merge worktrees itself. Concurrency stays capped at 2.

## Plan (each step test-first)

1. `snapshot.ts`: take, list, restore, prune snapshots; turn diff stats. Tests drive a fake `run`.
2. `failure.ts` + `src/failure.js` + `spark run`: record, trim, prompt text.
3. `mascot.ts`: face per state.
4. `agents.ts`: worktree parsing, test-command detection.
5. `register.tsx`: hooks, commands, band, panes. Engine tests for each command and hook.
6. MISP line, README, design doc, version 0.3.0, `npm test`, `npm run check`, release.

## Risks

- The mod API is early access; pane placement and `fs` access are only exercised through the test engine here.
- Snapshots hash new files each turn; huge untracked trees make `git add -A` slow, so it runs with a 10 s timeout and is skipped on failure with one toast.
